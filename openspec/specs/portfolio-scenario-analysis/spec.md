# portfolio-scenario-analysis Specification

## Purpose
한국·미국 보유 현황과 조회 가능한 주문 사실을 정확히 요약하고, 기존 시장 분석을 바탕으로 포트폴리오에 영향을 주는 기간별 시나리오를 제공한다.

## Requirements

### Requirement: 정규화된 금융 데이터 계산

시스템 MUST 시장, 거래소, 종목 코드, 통화, 기준 시각과 출처를 보존해야 한다. 종목 매핑은 명시적이어야 하며 실패하면 미지원으로 표시해야 한다. 금액은 Decimal 정밀도로 계산하고 KRW와 USD는 서로 환산한 근거와 환율 기준 시각이 있을 때만 합산해야 한다.

#### Scenario: 환율 누락

- **WHEN** KRW/USD 통합 비중이 필요하지만 유효한 환율이 없을 때
- **THEN** 통화별 금액과 비중만 제공하고 통합 합계를 만들지 않는다

#### Scenario: 매핑 미지원

- **WHEN** 토스 종목 코드를 기존 데이터 공급자 심볼로 명확히 매핑하지 못할 때
- **THEN** 해당 종목을 미지원으로 표시하고 다른 종목으로 대체하지 않는다

#### Scenario: 손익 자료 부족

- **WHEN** 매입원가, 실현 내역 또는 환차손익 계산 자료가 충분하지 않을 때
- **THEN** 수치 대신 미확인으로 표시하고 이를 추정하지 않는다

### Requirement: 계좌 전체 포트폴리오 요약

시스템 MUST 보유 비중, 현금성 비중, 평가손익, 종목·시장·통화 집중도를 코드로 계산해야 한다. 매수 가능 금액은 실제 현금 잔고와 구분해야 한다. 업종·상관관계는 자료가 있을 때만 분석해야 한다.

#### Scenario: 빈 포트폴리오

- **WHEN** 보유 종목과 매수 가능 금액이 모두 비어 있거나 0일 때
- **THEN** 빈 포트폴리오를 사실대로 표시하고 0을 임의로 채우지 않는다

#### Scenario: 주문 이력 요약

- **WHEN** 주문 목록·상세가 반환될 때
- **THEN** 주문·체결 수량, 상태, 거래 빈도 등 관측 가능한 사실만 요약하고 투자자의 의도나 심리를 추정하지 않는다

### Requirement: Toss 계좌 자료 조회 범위

시스템 MUST 지원되는 계좌 자료를 읽기 전용으로 조회하고, 환율 유효성·거래내역 페이지 한도·현재 보유 조회의 자산군 제한을 보고해야 한다. API가 반환한 원시 거래 레코드, 계좌 식별자 또는 거래 금액은 보고서에 보관하지 않아야 한다.

#### Scenario: 유효 환율 환산

- **WHEN** Toss가 현재 USD/KRW 참고 환율과 유효 시각을 반환할 때
- **THEN** 시스템은 매매기준율로 KRW/USD 통합 합계를 계산하고 참고 환율의 유효기간과 실제 체결 환율과 다를 수 있음을 표시한다
- **AND** 환율 유효 종료 시각이 지났거나 기준 시각을 확인할 수 없으면 통합 합계에 적용하지 않는다

#### Scenario: 거래내역 범위 요약

- **WHEN** Toss가 거래내역을 반환할 때
- **THEN** 시스템은 반환된 거래를 유형·자산군·결제 상태로 집계하고 페이지 한도 및 다음 페이지 여부를 표시한다
- **AND** 종료일 필터를 생략해 미결제 거래를 조회한다
- **AND** 원시 거래 레코드, 계좌 식별자, 종목별 거래 내역을 보고서에 포함하지 않는다
- **AND** 거래 금액을 기간 손익이나 현재 잔액으로 합산하지 않는다

#### Scenario: 옵션·채권 거래와 현재 보유 구분

- **WHEN** 거래내역에 옵션 또는 채권 거래가 포함되지만 현재 보유 API가 해당 자산군 잔액을 제공하지 않을 때
- **THEN** 시스템은 거래 이력만 요약하고 현재 수량·평가액·포트폴리오 비중은 미확인으로 유지한다

### Requirement: 기간별 시나리오

시스템 MUST 설정 가능한 단기(기본 1~20거래일), 중기(기본 1~6개월), 장기(기본 6~24개월)에 대해 상승·기본·하락 시나리오를 제공해야 한다. 각 시나리오는 논리, 근거와 출처 시각, 촉매, 관찰 조건, 검토 조건, 무효화 조건, 위험과 현재 포트폴리오 영향을 포함해야 한다. 계산·보정 방식이 없는 확률·예상 수익률·목표 가격을 제시해서는 안 된다. 분석 도구의 선택 인자가 생략되더라도 시스템 MUST 실행 기준일과 문서화된 기본 조회 범위를 사용해 조회를 시도해야 한다. 시장 분석은 보고서를 생성하기 전에 검증된 시장 스냅샷을 포함해야 한다.

#### Scenario: 날짜 인자 생략

- **WHEN** 분석 모델이 도구 호출에서 기준 날짜를 생략할 때
- **THEN** 시스템은 실행의 `trade_date`를 사용하고 그 이후 자료를 조회하지 않는다

#### Scenario: 뉴스 창 생략

- **WHEN** 분석 모델이 종목 뉴스 조회 기간을 생략할 때
- **THEN** 시스템은 실행 기준일에 끝나는 기본 7일 창을 조회한다

#### Scenario: 지표 선택 인자 생략

- **WHEN** 분석 모델이 기술 지표 조회에서 지표명을 생략할 때
- **THEN** 시스템은 지원되는 기본 지표 묶음을 조회하고, 실패한 값은 미확인으로 보고한다

#### Scenario: 검증 시세 조회

- **WHEN** 포트폴리오 심층 분석이 보유 종목을 조사할 때
- **THEN** 각 종목의 시장 분석은 OHLCV, 지표 및 최근 종가를 포함하는 검증 스냅샷을 조회하고 스냅샷을 기준으로 정확한 가격 주장을 작성한다

#### Scenario: ETF 펀더멘털

- **WHEN** 조회된 종목 유형이 ETF 또는 뮤추얼펀드일 때
- **THEN** 시스템은 펀드 프로필·운용·보유 자료를 조회하고 기업 재무제표를 펀드 실적처럼 해석하지 않는다

#### Scenario: 브로커 날짜 경계

- **WHEN** 로컬 UTC 날짜와 Toss API의 KST 날짜가 다르거나 주문 기간 종료일만 지정될 때
- **THEN** 시스템은 KST 기준 날짜를 사용하고 지정 종료일에 끝나는 30일 조회 창을 구성한다

#### Scenario: 공급자 범위 제한

- **WHEN** 브로커 또는 데이터 공급자가 특정 자산군·자료 형식·통화환산 정보를 제공하지 않을 때
- **THEN** 시스템은 커버리지 한계를 표시하고 값이나 완전성을 추정하지 않는다

#### Scenario: 근거가 부족한 기간

- **WHEN** 특정 기간의 자료나 종목 분석이 누락되었을 때
- **THEN** 성공한 다른 분석은 보존하고 누락 자료·기간·한계를 표시하며 근거 없는 시나리오 내용을 생성하지 않는다

#### Scenario: 제안 전용 언어

- **WHEN** 매매 관련 표현을 출력할 때
- **THEN** 분석 제안으로 표현하고 주문 생성·실행 지시 기능을 제공하지 않는다

### Requirement: 격리된 분석 실행

시스템 MUST 포트폴리오 상태를 기존 종목별 메모리와 체크포인트에 저장하지 않아야 한다. 관심종목은 사용자가 지정한 범위에서만 분석하고 동일 실행 안의 수집은 재사용해야 한다. 외부 뉴스와 문서는 신뢰할 수 없는 데이터로만 취급해야 한다.

#### Scenario: 합성 데이터 데모

- **WHEN** 데모 모드로 실행할 때
- **THEN** 인증정보·실제 계좌·실제 LLM 요청 없이 합성 데이터로 JSON과 한국어 Markdown을 생성한다

#### Scenario: JSON 계약 검증

- **WHEN** JSON 결과를 생성할 때
- **THEN** 명시된 결과 스키마를 검증하고 검증 여부를 사실 정확성이나 투자 성과 검증으로 설명하지 않는다

### Requirement: 시나리오 API 실패 원인 표시

시스템 MUST 심볼 조사와 시나리오 종합 API 실패를 안전한 오류 범주와 재시도 가능 여부로 표시해야 한다. 시스템 MUST 원시 예외, 공급자 응답 본문, 자격 증명 및 계좌 식별자를 보고서에 포함해서는 안 된다.

#### Scenario: 일부 심볼 조사 실패

- **WHEN** 일부 종목의 시장 조사 API 호출이 실패할 때
- **THEN** 성공한 분석은 보존하고 실패 종목에는 실패 범주와 재시도 가능 여부를 표시한다

#### Scenario: 시나리오 모델 호출 실패

- **WHEN** 시나리오 종합 모델 API 호출이 실패할 때
- **THEN** 포트폴리오 보고서에는 실패 범주와 재시도 가능 여부만 기록하고 원시 응답은 남기지 않는다

### Requirement: 보유 현황 기반 전체 결정 그래프

시스템 MUST 사용자가 `--full-workflow`를 지정하면 선택된 각 보유 종목에 대해 기존 TradingAgents의 분석가, Bull/Bear 조사 토론, Research Manager, Trader, Aggressive/Neutral/Conservative Risk 토론과 Portfolio Manager 최종 결정 단계를 순서대로 실행해야 한다. 그래프에는 계좌 식별자, 주문 이력, 원시 브로커 응답을 전달하지 않아야 한다. 현금 잔고가 확인되지 않으면 매수 가능 금액을 현금으로 간주하지 않아야 한다. 결과 보고서 MUST Trader 계획, Risk 토론, 최종 결정과 등급을 종목별로 표시하고 제안 전용으로 유지해야 한다.

#### Scenario: 전체 결정 워크플로 사용

- **WHEN** `portfolio live --full-workflow`가 선택된 보유 종목을 분석할 때
- **THEN** 기존 TradingAgents 결정 그래프가 전체 보유 현황 맥락에서 종목별로 실행된다
- **AND** 보고서에 Trader 계획, Risk 토론, Portfolio Manager 결정이 구분되어 표시된다
- **AND** 종목 조사는 전체 그래프 결과를 재사용하며 중복 조사 LLM 호출을 하지 않는다

#### Scenario: 기본 조사 모드 유지

- **WHEN** 사용자가 `--full-workflow`를 지정하지 않을 때
- **THEN** 기존 종목 조사와 포트폴리오 시나리오 경로 및 비용 특성을 유지한다

#### Scenario: 실제 현금 잔고 미확인

- **WHEN** 브로커가 실제 현금 잔고를 제공하지 않고 매수 가능 금액만 제공할 때
- **THEN** 매수 가능 금액은 Portfolio Manager 입력의 현금 잔고로 전달되지 않는다
- **AND** 각 보유 종목의 통화는 평균 매입가와 함께 명시된다

#### Scenario: 일부 종목 전체 그래프 실패

- **WHEN** 전체 결정 그래프가 일부 종목에서 실패할 때
- **THEN** 나머지 종목 분석은 보존하고 실패 종목의 안전한 오류 범주와 재시도 가능 여부를 보고한다
- **AND** 원시 예외, 인증정보, 계좌 식별자 및 원시 브로커 응답은 보고하지 않는다
